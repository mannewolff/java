1. Einführung und Ziele

Was die Toolbox ist, was sie leisten soll und für wen.

Die Toolbox ist eine Web-Anwendung im Dashboard-Stil: links die Navigation, rechts der Inhaltsbereich. Sie bündelt persönliche Werkzeuge an einem Ort, statt sie über verstreute Einzeltools zu verteilen. Die Anwendung ist als Single-User-Werkzeug konzipiert und läuft produktiv unter toolbox.mwolff.org.

Kernfunktionen

▦

Dashboards

Konfigurierbare Grid-Widgets (Textbox, KPI, Kanban-Vorschau) mit eigenem Layout pro Dashboard.
▣

Bild-Tools

Hintergrund entfernen (rembg/U2Net), Resize (LANCZOS), Crop für OG-Bilder, SVG nach PNG, Farbpalette.
▤

Kanban

Fünf Spalten (Backlog, Ready, In Progress, In Review, Done), Drag&Drop, Kommentare, Soft-Delete und automatisches Aufräumen erledigter Karten.
∿

Zeitreihen

Datenpunkt-Ingestion per Maschinen-Token (ohne Login), Visualisierung im Frontend.
⚿

Passwort-Generator

Rein clientseitig, ohne Server-Roundtrip.
⎙

Markdown nach PDF

Live-Vorschau im Frontend, Rendering über weasyprint.

4. Lösungsstrategie

Die Leitplanken, aus denen alles andere folgt.

AnsatzUmsetzung
Hexagonale ArchitekturPro Feature die Schichten domain, application, infrastructure, web. Die Domäne bleibt framework-frei, ArchUnit erzwingt die Pakethierarchie.
Proxy zu python-toolsSpring kapselt den Microservice: validiert den Upload, ergänzt das Shared-Secret, mappt Upstream-Fehler auf HTTP 502, ohne Details nach außen zu geben.
SPA + bearer-onlyFrontend hält das Token (PKCE), Backend ist zustandslos und prüft jedes JWT lokal über das JWK-Set. Nicht-API-Routen liefert der SpaForwardingController auf index.html aus.
Geplante Aufräum-JobsEin @Scheduled-Job räumt erledigte Kanban-Karten nach einer konfigurierbaren Aufbewahrungsfrist auf.
Strikte TestpyramideViele Unit-Tests, Slice-Tests pro Web-Schicht, Integrationstests gegen echte MariaDB (Testcontainers). 100 % Coverage und Mutation Score sind Pflicht.

6. Laufzeitsicht

Drei Abläufe, die das Zusammenspiel zeigen.

Login (PKCE)

  1. Der Browser startet den Authorization-Code-Flow mit PKCE gegen Keycloak.
  2. Nach erfolgreichem Login erhält das Frontend einen Code und tauscht ihn (mit code_verifier) gegen JWTs.
  3. Die Tokens landen in der Browser-Session. Jeder API-Aufruf trägt Authorization: Bearer <JWT>.
  4. Spring validiert das JWT lokal über das JWK-Set von Keycloak, ohne Rückfrage pro Request.

Bild-Tool ausführen (Hintergrund entfernen)

  1. Browser sendet POST /api/tools/remove-background mit Datei und Bearer-Token.
  2. Spring prüft Rolle USER, validiert den Upload (MIME, Größe) und ruft python-tools per RestClient auf, mit X-Internal-Key.
  3. python-tools verifiziert das Secret, entfernt den Hintergrund (rembg) und liefert ein PNG mit Alphakanal zurück.
  4. Spring gibt das Ergebnis an den Browser weiter, optionale Ablage im Bild-Speicher.

Zeitreihen-Ingestion ohne Login

  1. Ein externes System sendet POST /api/ingest/{token} mit dem Datenpunkt.
  2. Eine eigene Filter-Chain (IngestSecurityConfig, hohe Priorität) prüft den gehashten Token und die Gültigkeit.
  3. Ein Rate-Limiter pro Token greift, danach wird der Datenpunkt persistiert.
  4. Antwort 202 Accepted.

7. Verteilungssicht

Vier Container, ein Docker-Netz.

Der gesamte Stack läuft als Docker Compose, lokal wie produktiv. Nur API und Keycloak sind von außen erreichbar (in Produktion hinter einem Reverse-Proxy mit TLS). MariaDB und python-tools bleiben rein intern.

ServiceContainer-PortVon außenAufgabe
api (Spring Boot)8080127.0.0.1:8080, prod über ProxyAPI + ausgelieferter React-Build
keycloak8080127.0.0.1:8081, prod über ProxyIdentity, zwei Realms (dev/prod)
python-tools8000nein (nur intern)Bildverarbeitung, PDF
mariadb3306nein (nur intern)Persistenz, Schemas api + keycloak

Build und Rollout

Der Multi-Stage-Dockerbuild baut das Frontend (Node), packt das Spring-JAR inklusive React-Build nach classpath:/static (Maven, JDK 21) und liefert ein schlankes JRE-21-Image mit Non-Root-User aus. Auf dem Server folgt docker compose up -d. In Produktion serviert eine Domain alles, daher kein CORS.

Das Keycloak-Schema und die Realms werden nur beim ersten Start importiert. Bei bestehendem Volume greift der manuelle Fallback aus infra/keycloak/README.md. Theme-Änderungen werden erst nach force-recreate sichtbar.

8. Querschnittliche Konzepte

Was an vielen Stellen gleich gelöst ist.

Sicherheit

  • Authentifizierung über Keycloak (PKCE), Autorisierung über Realm-Rollen PENDING, USER, ADMIN, gemappt durch JwtAuthoritiesConverter.
  • Neue Registrierungen landen in PENDING und werden vom Admin manuell auf USER gesetzt.
  • Interner Service abgeschottet per Shared-Secret (X-Internal-Key), Ingest-Tokens nur gehasht (SHA-256) in der DB.
  • Keine Secrets, Tokens oder PII in Logs, keine Stacktraces nach außen.

Fehlerbehandlung

ExceptionAntwort
MethodArgumentNotValidExceptionHTTP 400 mit Feld-Fehlern
InvalidUploadExceptionHTTP 400 mit Code und Meldung
PythonToolsExceptionHTTP 502, generisch (kein Upstream-Leak)
unbehandeltHTTP 500 ohne Stacktrace

Datenbank-Migrationen

Flyway versioniert das Schema (V1__…sql aufwärts). Migrationen sind one-way, Rollback erfolgt bewusst manuell. baseline-on-migrate akzeptiert bestehende Schemata. Spätere Wellen ergänzen unter anderem Kanban-Kommentare, Soft-Delete, Bild-Speicher mit User-Isolation und das Versions-Tracking.
